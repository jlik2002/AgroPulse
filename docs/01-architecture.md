# Архитектура

## Сервисы

| Сервис | Роль | Во что упирается |
|---|---|---|
| `api` | FastAPI: REST и поток прогресса SSE | ничего долгого не выполняет |
| `worker-collect` | Celery: обращения к GEE и Open-Meteo | сеть |
| `worker-analyze` | Celery: норма, аномалии, риск, отчёты | CPU |
| `postgres` | PostGIS: полигоны, наблюдения, аномалии, прогнозы | |
| `redis` | брокер Celery, кэш внешних API, шина прогресса | |
| `minio` | PDF-отчёты, превью снимков, кэш растров | |
| `web` | nginx: раздача SPA, проксирование `/api` | |
| `migrate` | одноразовый шаг миграций | |

Две очереди Celery разделены потому, что сбор ждёт сеть, а анализ считает: в Kubernetes это два Deployment с разными ресурсами.

Миграции вынесены в отдельный шаг, а не в старт приложения: несколько реплик API накатывали бы их наперегонки.

## Сущности

**Поле** — контур, временной ряд, аномалии, балл риска. Единица расчёта.

**Проект** — рабочее пространство с общим периодом наблюдения. Период общий, иначе поля несопоставимы при ранжировании. Регистрации нет: владелец берётся из cookie, ссылка на проект открывает его любому.

**Хозяйство** — сельхозпроизводитель, которому принадлежат поля. Справочник общий и проекту не принадлежит: название, ИНН и район от периода не зависят.

```
Проект ──< Поле >── Хозяйство
  │         │
  │         ├─< Наблюдение (NDVI, NDMI, EVI, погода)
  │         ├─< Радарное наблюдение (Sentinel-1)
  │         ├─< Аномалия
  │         └── Прогон прогноза
  └─< Документ
```

Радарные наблюдения лежат отдельной таблицей: радар меряет обратное рассеяние, а не отражение, и своя сетка дат у него не совпадает с оптической.

## Слои бэкенда

```
api/routers/   HTTP: коды ответов, заголовки. Бизнес-логики нет
schemas/       контракт наружу, отделён от моделей хранения
services/      сценарии, границы транзакций
repositories/  весь SQL
db/models.py   схема
analytics/     чистые расчёты, работают без базы
providers/     внешние источники за общими интерфейсами
tasks/         задачи Celery
```

Границу транзакции задаёт сервис через `UnitOfWork`, репозиторий `commit` не вызывает.

Ошибки предметной области (`errors.py`) не знают про HTTP: одна операция вызывается из роутера, из Celery и из CLI. Код ответа проставляет обработчик.

## Идемпотентность

Celery настроен с `task_acks_late`, поэтому при рестарте воркера задача выполнится повторно. Наблюдения пишутся upsert по ключу `(field_id, date, value_type, source)`. Результаты анализа замещаются целиком в одной транзакции.

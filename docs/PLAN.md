# AgroPulse — план разработки

## Context

Команда участвует в Космохакатоне с задачей мониторинга вегетационной динамики сельхозполей.
ТЗ (`постановка задачи.pdf`) требует **две воспроизводимые точки входа**: веб-сервис, где
пользователь указывает регион и выбирает/рисует полигон, а сервис сам собирает спутниковые и
метеоданные, восстанавливает пропуски `primary_ndvi` и показывает аномальные периоды; и
технический batch-инференс `private_features.csv → submission.csv`.

ML-модели (восстановление пропусков — задача 1 с метрикой RMSE/GapScore, и детекция аномалий)
делает другой участник команды отдельным сервисом. **Всё остальное — бэкенд, дата-пайплайн,
аналитику, отчёты, инфраструктуру и фронтенд — делает один человек.** Целевой объём —
`product_vision_agropulse.md` целиком.

Из 100 баллов критериев 30 приходятся на метрику (чужая зона), остальные ~60 — на нашу:
работа с аномалиями и регионами (27), UX (10), исследовательский отчёт (10), код и документация (8).
Плюс два требования, которые легко забыть: **комментарии в коде на русском языке** и
**запуск по README без единой правки исходников**.

Репозиторий сейчас пуст — есть только vision, два PDF и `.gitignore` под Python.

## Зафиксированные решения

| Решение | Выбор | Почему |
|---|---|---|
| Бэкенд | FastAPI | решено командой |
| Окружение | docker compose (основная точка запуска для экспертов) | прямой критерий воспроизводимости |
| Очередь задач | **Celery + Redis** (broker и result backend) | выбор пользователя; prefork-воркер хорошо ложится на синхронные `earthengine-api` / `rasterio` / `numpy` |
| Спутник | Sentinel-2 через **GEE**, фолбэк — STAC (Planetary Computer) | GEE зарегистрирован; требование быстро пересесть |
| Погода | **Open-Meteo** (архив ERA5 + прогноз 14 дней), сверка с GEE ERA5-Land | в GEE нет прогноза, а он нужен по vision §8.8 |
| Контуры полей | Overpass API (OSM `landuse=farmland`), маска ESA WorldCereal | vision §8.1, критерий «адаптивность под регионы» |
| LLM | OpenRouter | решено командой |
| Обмен с ML | **REST** (контракт ниже), возможен переезд на брокер позже | выбор пользователя |
| Хранилище артефактов | **MinIO / S3-совместимое** | поды остаются stateless, один код в compose и k8s |
| БД | PostgreSQL + PostGIS | геометрия полигонов, `ST_Area(geography)` |
| Оркестрация | **Helm chart**, проверяем локально в **kind** | выбор пользователя |
| Фронтенд | React + Vite + TS + Tailwind + shadcn/ui; карта `react-leaflet` + `leaflet-geoman`, подложка CARTO Positron; графики ECharts; `react-compare-slider` | «легко и можно сделать красиво», без API-ключей |

## Архитектура

```
api        FastAPI — REST + SSE. Ничего долгого не делает
worker     Celery prefork. Очереди: collect (медленный GEE) и analyze (быстрая аналитика)
postgres   PostGIS
redis      брокер Celery + кэш внешних API + pub/sub прогресса стадий
minio      PDF, превью снимков, кэш растров
web        React SPA за nginx
────
ml-service чужой, по REST через адаптер
```

Разделение очередей `collect` / `analyze` — не украшение: в k8s это два Deployment'а
с разными ресурсами и независимым масштабированием.

## Контракт с ML-сервисом (REST) → `docs/ML_API.md`

```
GET  /health
GET  /v1/model-info    → {model_version, expected_features: [...], supports: [...]}
POST /v1/impute        → восстановление primary_ndvi
POST /v1/forecast      → прогноз NDVI на 14 дней
POST /v1/detect        → опционально, если детекция модельная
```

`POST /v1/impute` — один эндпоинт обслуживает **и** веб-сценарий, **и** `submission.csv`:

```jsonc
// запрос
{"request_id": "...", "series": [{
  "polygon_id": "...", "crop_type": "wheat|null",
  "observations": [{"date": "2025-06-01", "primary_ndvi": 0.62, "features": {...}}],
  "targets": ["2025-06-14", "2025-06-19"]     // даты, которые нужно восстановить
}]}
// ответ
{"request_id": "...", "model_version": "v3", "predictions": [
  {"polygon_id": "...", "date": "2025-06-14", "primary_ndvi_pred": 0.543, "confidence": 0.81}]}
```

`GET /v1/model-info` обязателен: на старте сверяем `expected_features` с нашим
`features/contract.py` и падаем с внятной ошибкой, а не выдаём мусор. Это главная
митигация риска №1.

## Инварианты, заданные требованием k8s

Их закладываем **с первого этапа** — переделывать потом дорого:

1. **Никаких файлов на локальном диске** — PDF, превью, кэш растров только через `storage/s3.py`.
2. **Конфиг только из env**; GEE service-account JSON — Secret, монтируется файлом.
3. **`/health/live` и `/health/ready` раздельно** — используются и в compose healthcheck, и в probes.
4. **Миграции — отдельный шаг, не в старте приложения.** В compose сервис `migrate`,
   в Helm — Job с хуком `pre-install,pre-upgrade`. Иначе при нескольких репликах гонка.
5. **Задачи идемпотентны.** С `task_acks_late=True` + `worker_prefetch_multiplier=1` задача
   при рестарте пода выполнится повторно — значит наблюдения пишутся `upsert` по
   `(field_id, date, source)`, а не `insert`.
6. **SSE через Redis pub/sub**, а не через память процесса — любая реплика `api` отдаёт поток.
7. **Graceful shutdown**: сбор по полю занимает минуты, поэтому `terminationGracePeriodSeconds: 300`
   и warm shutdown Celery по SIGTERM.

## Этапы

Порядок — вертикальными срезами: каждый этап заканчивается чем-то демонстрируемым.

### E0. Каркас
`docker-compose.yml` (api, worker, postgres+postgis, redis, minio, migrate), `config.py`,
`db/models.py` + первая миграция Alembic, `health.py`, `storage/s3.py`, `tasks/celery_app.py`.
Схема БД: `projects`, `fields` (geometry 4326), `observations`, `anomalies`, `forecasts`,
`jobs`, `scene_assets`, `raw_cache`.

### E1. Гео-ядро и срез до NDVI ⭐ самый важный этап
Снимает главный технический риск в первый же день.
- `POST /api/projects` → `POST /api/projects/{id}/fields` (GeoJSON), площадь через `ST_Area(geography)`
- `providers/satellite_gee.py`: поиск сцен `COPERNICUS/S2_SR_HARMONIZED`, маска облаков
  **SCL (классы 3, 8, 9, 10, 11) + `S2_CLOUD_PROBABILITY`**, `NDVI mean`, `valid_fraction`,
  `cloud_fraction`, `scene_id`. Ряд забирать **одним** `getRegion().getInfo()`, не циклом по датам
- Celery-задача `collect_field_data`, `GET /api/fields/{id}/timeseries`

**Готово, когда:** нарисованный полигон → JSON с рядом NDVI по датам.

### E2. Полный дата-слой и устойчивость
- `satellite_stac.py` — фолбэк, тот же протокол (пишем сразу, пока помним семантику полей)
- `weather_openmeteo.py` — архив + прогноз 14 дней
- NDMI (`B8/B11`) и EVI на том же проходе
- `providers/cache.py` + `raw_cache`, retry с backoff; источник упал → `missing_reason`, не 500
- Автоподгрузка **истории за 3–5 предыдущих сезонов** (vision §7 шаг 4) — основа климатологии
- `parcels_overpass.py` + геокодинг региона через Nominatim

**Готово, когда:** «нашёл регион по названию → увидел контуры пашни → выбрал → получил ряд с погодой и качеством данных».

### E3. Оркестрация и прогресс
Enum из 9 стадий ровно как в vision §7; `tasks/progress.py` публикует в Redis pub/sub;
`GET /api/projects/{id}/events` — SSE. Пообъектная устойчивость: одно поле упало — остальные
считаются, статус `недостаточно данных`. Статусы поля: критический / требует внимания /
аномалий нет / недостаточно данных.

### E4. Аналитика ⭐ здесь 7 баллов за детекцию
- `climatology.py` — норма по собственной истории поля: медиана и std по `day-of-year`,
  со сдвигом на дату посева, если указана
- `anomalies.py` — z-score по формуле из ТЗ, пороги −1 / −2; устойчивые негативные отклонения →
  склейка соседних → длительность, максимум отклонения, уверенность
- Контекст: сопоставление с NDMI, температурой, осадками — отделяем погодный стресс от смены
  фазы, облаков и ошибок данных (пункт 3 теоретического раздела ТЗ)
- `risk.py` — составной риск с раскрытием вклада факторов, ранжирование полей
- Восстановление пропусков пока `ml/baseline.py` (Savitzky-Golay)

**Готово, когда:** на демо-полигоне находится реальная просадка вегетации с объяснением.

### E5. ML-интеграция и batch
`ml/client.py` (протокол), `ml/http_client.py` (REST, таймауты, фолбэк на baseline),
`features/contract.py`, сверка с `/v1/model-info` при старте.
`value_type`: observed / restored / forecast — физически разные записи.
Прогноз на 14 дней + доверительный интервал.
`cli.py`: `python -m agropulse.cli predict --input private_features.csv --output submission.csv`
плюс валидатор сабмита (ровно одна строка на `anon_polygon_id + date`, без NaN и лишних строк,
UTF-8, запятая) — отдаём напарнику, сэкономит ему прогоны на платформе.

### E6. LLM и экспорт
`llm/openrouter.py` + промпты на русском, вход — **только проверенный JSON**.
`llm/validator.py`: каждое число и дата в тексте должны встречаться в исходном JSON, иначе
перегенерация (vision §12). CSV ровно с колонками vision §10. PDF через WeasyPrint + Jinja2:
отчёт по полю и сводный.

### E7. Фронтенд
После стабилизации API. Порядок экранов: карта → страница поля → сводный дашборд →
предпросмотр отчёта. Стек из таблицы решений.

### E8. Kubernetes
Основная работа уже сделана инвариантами выше, остаётся сам чарт:
- Deployments: `api` (2 реплики), `worker-collect`, `worker-analyze`, `web`
- StatefulSet `postgres`, `redis`, `minio` для dev-профиля; в `values.yaml` — переключатели
  на внешние managed-сервисы
- Secret (GEE JSON, ключ OpenRouter, креды БД), ConfigMap для остального
- Job миграций как Helm hook `pre-install,pre-upgrade`
- Ingress: `/` → web, `/api` → api, с `nginx.ingress.kubernetes.io/proxy-buffering: "off"`
  и увеличенным read timeout — иначе SSE не работает
- HPA по CPU для `api`; **KEDA ScaledObject** для `worker-collect` по длине списка очереди
  в Redis — заодно готовый пункт «дополнительные идеи» в презентации
- `values-kind.yaml` + `deploy/helm/README.md` с командой прогона в kind

### E9. Упаковка под сдачу
README (стек, структура, `docker compose up`, обе команды запуска, настройка GEE-ключа,
входные/выходные файлы), seed-скрипт с 2–3 демо-полигонами и прогретым кэшем,
`docs/RESEARCH.md` (наша часть: источники данных, логика детекции, эксперименты по маскам
облаков; часть про интерполяцию — от напарника), прогон демо-сценария vision §18 целиком.

## Риски

1. **Расхождение признаков с ML-моделью** — главный. Модель учится на `train_dataset.csv`,
   а сервис собирает данные из GEE сам. Разъедется нормировка индексов, определение
   климатологии или окно осреднения погоды — модель на живых данных даст мусор, и узнаем мы
   об этом за день до сдачи. Митигация: единый `features/contract.py`, `/v1/model-info`,
   и тест «прогнать через наш пайплайн полигон, для которого известен `train_dataset.csv`,
   и сверить значения».
2. **GEE** — квоты, `EEException` под нагрузкой. Митигация: провайдер-абстракция с E1,
   STAC-реализация пишется на E2, а не в последний момент.
3. **Фронтенд в одиночку** — много экранов. Митигация: делаем после стабилизации API,
   на готовых компонентах, начиная с самого «продаваемого» экрана.

## Открытый вопрос: качество детекции аномалий

Отложено сознательно — вопрос комплексный и требует отдельной проработки,
а не точечных правок. Базовая детекция работает и закрывает сценарий, но
на реальных данных вскрылись ограничения, которые нужно решать системно.

### Что уже выяснено на практике

**Севооборот ломает принцип «поле сравнивается само с собой».** На Кубани поле
с озимой пшеницей, убранной в июле, на фоне нормы, построенной по прошлым
сезонам с пропашными культурами, даёт z = −2.05 за период уборки. Формально
это аномалия, фактически — плановая уборка урожая.

**Первая версия защиты оказалась негодной.** Проверка «сезон уходит и выше
нормы, и ниже» вырождалась в «есть глубокая аномалия»: при короткой истории
норма узкая, и верхний порог превышали все поля, включая эталонные. Защита
резала риск любому настоящему событию.

**Рабочая мера — форма кривой, а не глубина отклонения.** Корреляция Пирсона
между фактическим сезоном и нормой поля разделяет случаи: 0.97 у эталонного
поля Айовы, 0.35 у кубанского поля со сменой культуры. Порог 0.75 подобран
на четырёх полях двух регионов.

### Что требует решения

- **Порог корреляции подобран на четырёх полях.** Одно из них (Кубань-1,
  r = 0.783) сидит вплотную к границе. Нужна валидация на выборке в десятки
  полей с известным севооборотом.
- **Уборка урожая не отделена от угнетения.** Резкое падение с высоких
  значений до уровня открытой почвы — распознаваемое событие, его стоит
  детектировать явно, а не глушить через корреляцию.
- **Норма по короткой истории неустойчива.** Три-четыре сезона дают узкий
  разброс, из-за чего z-score легко улетает за ±2 на обычной межгодовой
  изменчивости. Возможные направления: гибридная норма «история поля +
  культура + регион», робастные оценки разброса, увеличение глубины истории.
- **Пороги z взяты из постановки задачи и не проверялись на наших данных.**
  Нужна оценка precision и recall на размеченных случаях.
- **Оценка уверенности эвристическая.** Веса в составном риске подобраны
  из практических соображений, а не оптимизацией; их вклад стоит проверить
  абляциями.

Подробности замеров и разбор обеих неудачных версий — в `docs/RESEARCH.md`.

## Производительность: почему остаёмся на чистом Python

Обсуждали вынос расчётов на другой язык. Не делаем, и вот куда на самом деле уходит время.

- **GEE-путь (основной).** NDVI считается на серверах Google. Наш код формирует граф вычислений
  и ждёт HTTP-ответ — переписывание на Rust/Go ускорит сборку JSON-запроса, то есть ничего.
- **STAC-фолбэк.** 80–90% времени — сеть и IO; декодирование GeoTIFF делает GDAL (C++),
  арифметику индексов — numpy (C + SIMD). Python здесь тонкая обёртка вокруг нативного кода.
- **Аналитика.** Сотни-тысячи точек на поле, numpy считает за миллисекунды. Не горлышко.

Что действительно ускоряет, по убыванию эффекта — всё уже заложено в план:

1. Кэш внешних вызовов (`providers/cache.py`, E2) — повтор того же полигона и периода не идёт наружу.
2. Один `getRegion().getInfo()` на всю историю вместо цикла по датам (E1) — разница на порядок.
3. Параллелизм по полям: Celery с несколькими воркерами, поля независимы.
4. Чтение нужного уровня пирамиды COG вместо полного разрешения 10 м — до 4–16x на IO.
5. Воспринимаемая скорость: SSE-прогресс по стадиям и выдача полей по мере готовности (E3).

Язык имел бы значение только при попиксельных циклах на чистом Python — их у нас нет.
Если профилирование когда-нибудь покажет CPU-bound участок, там хватит `numba.njit`,
а не отдельного сервиса. Цена второго языка — второй Dockerfile, второй набор зависимостей,
IPC и отладка в одиночку; при этом баллов за скорость расчётов в критериях нет,
а за «запускается по инструкции без правок» — есть.

критерия «адаптивность под множественные регионы». Отдельно: выключить сеть до GEE и убедиться,
что STAC-фолбэк отрабатывает, а не роняет пайплайн.

**E4:** на поле с известной засухой сервис отдаёт аномальный период с `z < -2` и совпавшими
погодными факторами.

**E5:** `python -m agropulse.cli predict --input private_features.csv --output submission.csv` →

**E8:** `kind create cluster` → `helm install agropulse deploy/helm/agropulse -f values-kind.yaml` →

## E10. Sentinel-1: радар как независимое подтверждение

Дата: 5 сентября 2026.

Оптика отвечает на вопрос «что со спектральным состоянием растений», радар —
«изменилась ли их структура и поверхность под ними». Механизмы измерения
разные и независимые, поэтому совпадение аномалии в обоих источниках повышает
доверие к выводу сильнее, чем любое количество дополнительных оптических
индексов. Плюс радар не зависит от облачности: там, где оптический ряд рвётся
на две недели, радарный продолжается.

Ключевое решение: **радар не участвует в поиске аномалий и не меняет их
границы**. Событие по-прежнему находится по NDVI. Радар отвечает на отдельный
вопрос — сошлись ли на этом событии независимые способы измерения, — и его
ответ живёт в отдельном показателе `corroboration`.

### Что сделано

**Источник.** `providers/radar_gee.py`, коллекция `COPERNICUS/S1_GRD` — уже
откалиброванная, с убранным тепловым шумом и коррекцией рельефа. Режим `IW`,
поляризации `VV + VH`. На каждую дату по полю считаются: медианы `VV` и `VH`
в децибелах, разность `VH − VV`, `RVI` (в линейных значениях, затем медиана),
межквартильный размах `VV` как мера неоднородности, доля площади с пониженным
сигналом, доля покрытия полосой съёмки.

**Обязательные предосторожности** — все реализованы, каждая закрывает
конкретный способ получить выдуманное событие:

| Мера | Что было бы без неё |
|---|---|
| Фильтр режима `IW` | ряд смешал бы съёмки разного разрешения и угла |
| Медиана вместо среднего | техника, строение или столб внутри контура тянули бы значение |
| Медианный фильтр 30 м | спекл превратил бы долю слабых пикселей в замер шума |
| Внутренний отступ 20 м | краевые пиксели контура — это дорога и лесополоса |
| Разности только внутри одной орбиты | смена геометрии съёмки читалась бы как событие |
| Разрыв больше 30 суток разностью не считается | пропуск в ряду выглядел бы скачком |
| Два пролёта в один день не усредняются | среднее не соответствует ни одной реальной геометрии |
| Покрытие ниже 50% — пропуск с причиной | медиана считалась бы по случайному куску поля |
| Нулевое покрытие — сцена выбрасывается | `filterBounds` отбирает по рамке снимка, а она шире полосы съёмки: ряд засорялся бы пролётами, поля не касавшимися |
| Уровень сравнивается с нормой своей орбиты | разница углов падения вошла бы в z-score как отклонение состояния поля |

Отдельная история — сцены, где поле оказалось за краем полосы съёмки.
Медиана по такой сцене возвращается пустой, и арифметика над ней роняла
**весь** серверный запрос: одна сцена 2019 года лишала поле всего радарного
ряда за пять сезонов, причём тихо — ошибка уходила в `errors` качества данных,
а ряд просто оставался пустым. Обнаружено только на живом поле в Краснодарском
крае; на поле в Айове, где каждая сцена накрывает контур целиком, дефект
не воспроизводился.

**Производные величины** (`analytics/radar.py`): `ΔVV`, `ΔVH`, `ΔRVI` к
предыдущему снимку той же орбиты и `change_point_score` — ранг величины скачка
в собственной истории поля. Ранг, а не порог в децибелах: у поля под
многолетними травами и под пропашной культурой «обычная» величина скачка
разная, и общего порога не существует.

**События.** Резкое падение `VH` → изменение структуры растительности; сдвиг
`VV` при неизменном `VH` → изменение состояния поверхности. Рост событием не
считается — по той же причине, по которой им не считается рост NDVI: это
нормальное развитие покрова, а не повод ехать в поле. Причина никогда не
называется: одно и то же падение возможно при уборке, скашивании, полегании,
потере массы и естественном завершении вегетации. Наружу уходит перечень
гипотез.

**Подтверждение следующим снимком — то, без чего события бесполезны.** Первая
версия отбирала события по порогу в децибелах, и на реальном поле кукурузы
в Айове дала двенадцать событий за сезон, из них шесть в апреле-мае по голой
почве: обратное рассеяние там определяется влажностью верхнего слоя, и после
дождя сигнал уходит на 4-7 дБ, а через неделю возвращается. По порогу всё это
выглядело уборкой.

Настоящее структурное изменение необратимо, поэтому событием считается только
то, которое удержалось на следующей съёмке той же орбиты. Скачок, отыгранный
назад больше чем на 40%, отбрасывается. Плюс для `VV` отдельный, вдвое больший
порог: канал поверхности по природе волатильнее. После обеих поправок то же
поле даёт четыре события за сезон и ни одной ложной «уборки».

**Подтверждённость события** (`corroborate`), 0..100: оптика 30 (15, если
больше половины точек периода восстановлены моделью), радар 20, устойчивость
во времени 20, погодное объяснение 20; штрафы −20 за сплошную облачность
в окне и −20 за подтверждение, опирающееся на единственную съёмку пригодной
к сравнению орбиты.

Радар подтверждает по двум независимым признакам, и любого достаточно:
уровень `VH` ниже собственной нормы поля для этой фазы сезона (полог слабее
обычного) либо подтверждённое резкое падение внутри окна (структура резко
изменилась именно тогда). Поле могло войти в аномалию с запасом по уровню
и всё равно просесть, и наоборот.

Проверено на кубанском поле: аномалия NDVI 11-18 июля собрана на 75% из
восстановленных точек под 66% облачности, а радар в те же дни показал
VH −16,9 дБ против нормы −18,2 за четыре прошлых сезона — полог не угнетён.
Оценка 35 из 100, «низкая». Это ровно тот случай, ради которого радар
и добавлялся: облачный артефакт оптики виден как неподтверждённый.

**Хранение.** Отдельная таблица `radar_observations`, а не строки в
`observations`. Причина физическая: обратное рассеяние и оптическое отражение —
разные величины, общий ряд сделал бы бессмысленными и график NDVI, и
климатическую норму, и выгрузку. Плюс у Sentinel-1 своя сетка дат.

**Наружу.** Стадия `radar` в пайплайне, эндпоинт `GET /fields/{id}/radar`,
блок на вкладке «Динамика» с рядом и списком событий, раздел «Радарная съёмка
Sentinel-1» в отчёте по полю, подтверждённость в карточке каждой аномалии.

### Чего сделать не удалось и почему

Всё перечисленное ниже требует **попиксельного** анализа, а весь пайплайн
построен на сведении поля к одному числу на дату. Это не мелкая доработка:
меняется форма запроса к Earth Engine, объём ответа, схема хранения и способ
показа. Ни одно из этого не сделано, и обещать этого в презентации нельзя.

1. **`anomalous_area_fraction` в исходном смысле — доля пикселей, аномальных
   относительно собственной истории.** Реализована более слабая величина:
   `low_signal_fraction` — доля площади, где сигнал ниже медианы **самого поля
   на эту дату** более чем на 2 дБ. Это мера неоднородности внутри даты,
   а не отклонения от нормы. Настоящий вариант требует попиксельной
   климатологии: норму нужно строить для каждого пикселя за 4 сезона,
   то есть держать растр нормы на поле, а не одно число.

2. **Пространственная локализация аномалии** («западная часть поля»,
   «аномальная зона занимает 14%»). Требует вернуть из Earth Engine геометрию
   или растр аномальной зоны, положить его в объектное хранилище и научить
   карту его показывать. Ни хранения масок, ни слоя на карте под это нет.

3. **Зонирование поля** — устойчиво нормальная зона, устойчиво отличающаяся,
   недавно появившаяся аномалия. Надстройка над пунктом 2, и без него смысла
   не имеет.

4. **Пространственное совпадение аномалий в оптике и радаре** — тот самый
   вклад +10 в оценке подтверждённости. Константа `WEIGHT_SPATIAL` объявлена
   и не используется: без пунктов 2 и 3 совпадение не с чем сравнивать.
   Практическое следствие: достижимый максимум оценки равен 90, а не 100,
   и «идеально подтверждённого» события у нас пока не бывает. Это осознанно
   и описано в коде.

5. **Радар как замена оптики под облаками.** Сейчас радарный ряд отображается
   и порождает события, но восстановление пропусков NDVI по радару (подход
   уровня ESA CropSAR) не реализовано: `ml/impute` работает только с
   оптическим рядом. Событие под сплошной облачностью будет видно
   в радарном блоке, но в ряд NDVI не попадёт.

6. **Угол падения луча** (`angle`) не сохраняется. Вместо него для
   сопоставимости используются направление пролёта и относительный номер
   орбиты — этого достаточно, чтобы не сравнивать несравнимое, но
   нормализация сигнала по углу невозможна.

### Отдельно: расширение оптики, которое напрашивается, но не сделано

Дёшево на стороне Earth Engine (одно выражение в том же запросе), но каждый
пункт тянет за собой колонку в базе, миграцию, колонку в выгрузке, серию
на графике и строку в отчёте — то есть это отдельный проход, а не довесок:

- **NDRE** (`B8`, `B5`) — хлорофилл, реагирует на азотное голодание раньше NDVI;
- **NDWI** (`B3`, `B8`) — открытая вода и переувлажнение;
- **Перцентили `p10`, `p90` и IQR по NDVI** — неоднородность поля в оптике,
  прямой аналог уже посчитанного `spatial_iqr_db` в радаре. Из всех трёх
  пунктов этот самый ценный: он даёт оптическую половину для сравнения
  неоднородности между источниками.

# Контракт с сервисом ML-моделей

Документ фиксирует, как веб-сервис AgroPulse обращается к сервису моделей
восстановления пропусков NDVI и прогноза. Обмен — по REST поверх HTTP, JSON в обе
стороны, кодировка UTF-8.

Транспорт может быть заменён на брокер сообщений позднее: со стороны AgroPulse
за обращения отвечает один адаптер (`backend/agropulse/ml/http_client.py`),
и смена транспорта не затрагивает остальной код.

Базовый адрес задаётся переменной `ML_SERVICE_URL` (по умолчанию `http://ml-service:8000`).

---

## Общие правила

- Даты — строки `YYYY-MM-DD`.
- Числа с плавающей точкой — обычные JSON-числа, `NaN` и `Infinity` недопустимы.
- Отсутствующее значение передаётся как `null`, а не как `0` или пустая строка.
- Идентификатор полигона (`polygon_id`) непрозрачен для сервиса моделей: в веб-сценарии
  это UUID поля, в batch-сценарии — `anon_polygon_id` из тестового набора.
- Любой ответ с кодом, отличным от 2xx, или превышение таймаута
  (`ML_SERVICE_TIMEOUT_SECONDS`, по умолчанию 120 с) переводят AgroPulse на
  локальный baseline, а результат помечается пониженной достоверностью.

---

## `GET /health`

Проба доступности. Ответ `200` с любым телом считается успехом.

---

## `GET /v1/model-info`

Описание подключённой модели. AgroPulse вызывает этот метод при старте и сверяет
`expected_features` с собственным построителем признаков.

```json
{
  "model_version": "gbdt-v3",
  "expected_features": ["ndvi_lag1", "ndvi_lead1", "doy_sin", "doy_cos", "t2m_mean_7d", "..."],
  "supports": ["impute", "forecast"]
}
```

**Зачем это нужно.** Модель обучается на `train_dataset.csv`, а AgroPulse собирает
признаки самостоятельно из Google Earth Engine. Если состав или семантика признаков
разойдутся, модель на живых данных даст правдоподобный, но неверный результат.
Сверка на старте превращает такую рассинхронизацию в явную ошибку конфигурации.

---

## `POST /v1/impute`

Восстановление пропущенных значений `primary_ndvi`.

Метод обслуживает оба сценария: и веб-интерфейс, и формирование `submission.csv`.
Разница только в том, откуда взяты наблюдения и какие даты запрошены.

### Запрос

```json
{
  "request_id": "0f1c2d3e-...",
  "series": [
    {
      "polygon_id": "AOI-0001",
      "crop_type": "wheat",
      "observations": [
        {
          "date": "2025-06-01",
          "primary_ndvi": 0.62,
          "features": {"ndmi": 0.31, "t2m_mean": 21.4, "tp_sum": 0.0}
        },
        {
          "date": "2025-06-14",
          "primary_ndvi": null,
          "features": {"ndmi": null, "t2m_mean": 24.8, "tp_sum": 0.0}
        }
      ],
      "targets": ["2025-06-14"]
    }
  ]
}
```

| Поле | Тип | Описание |
|---|---|---|
| `request_id` | string | Идентификатор запроса, возвращается в ответе для сопоставления |
| `series[].polygon_id` | string | Идентификатор полигона |
| `series[].crop_type` | string \| null | Культура текущего сезона. Обязательна при заведении поля, поэтому заполнена всегда, кроме полей, созданных до введения этого правила |
| `series[].observations` | array | Весь доступный ряд полигона, включая строки с пропусками |
| `observations[].primary_ndvi` | float \| null | `null` для дат, подлежащих восстановлению |
| `observations[].features` | object | Признаки строки; состав описан в `expected_features` |
| `series[].targets` | array | Даты, для которых требуется предсказание |

Ряд передаётся целиком, а не только окрестность пропуска: модели может
понадобиться и сезонный контекст, и история предыдущих лет.

### Ответ

```json
{
  "request_id": "0f1c2d3e-...",
  "model_version": "gbdt-v3",
  "predictions": [
    {
      "polygon_id": "AOI-0001",
      "date": "2025-06-14",
      "primary_ndvi_pred": 0.543218,
      "confidence": 0.81
    }
  ]
}
```

`confidence` необязателен. Если модель его не отдаёт, AgroPulse считает уверенность
неизвестной и не показывает пользователю числовую оценку.

На каждую пару `polygon_id` + `date` из `targets` должна прийти ровно одна строка
предсказания.

## `POST /v1/forecast`

Прогноз NDVI на горизонт вперёд (по умолчанию 14 дней).

### Запрос

```json
{
  "request_id": "…",
  "horizon_days": 14,
  "series": [
    {
      "polygon_id": "AOI-0001",
      "crop_type": "wheat",
      "sowing_date": "2025-04-18",
      "observations": [{"date": "2025-06-01", "primary_ndvi": 0.62, "features": {}}],
      "weather_forecast": [
        {"date": "2025-07-02", "t2m_mean": 26.1, "tp_sum": 0.0}
      ]
    }
  ]
}
```

### Ответ

```json
{
  "request_id": "…",
  "model_version": "gbdt-v3",
  "forecasts": [
    {
      "polygon_id": "AOI-0001",
      "direction": "declining",
      "risk_level": "high",
      "confidence": 0.64,
      "insufficient_reason": null,
      "points": [
        {"date": "2025-07-02", "ndvi_pred": 0.51, "ndvi_lo": 0.44, "ndvi_hi": 0.58}
      ]
    }
  ]
}
```

Если данных для прогноза недостаточно, сервис возвращает пустой `points` и
заполняет `insufficient_reason`. AgroPulse в этом случае прогноз не показывает,
а сообщает пользователю причину — искусственный прогноз хуже его отсутствия.

---

## `POST /v1/detect` (необязательный)

Детекция аномалий, если она выполняется моделью, а не правилами на стороне AgroPulse.
Пока метод не реализован, AgroPulse использует собственную детекцию по z-score
относительно климатической нормы поля.

---

## Что требуется от стороны моделей

1. Точный список колонок `train_dataset.csv` и их семантика: как рассчитана
   климатическая норма, какое окно осреднения у погодных признаков, как нормированы
   спутниковые индексы. Без этого признаки на живых данных не совпадут с обучающими.
2. Подтверждение или правки этого контракта.
3. Значение `expected_features`, отдаваемое `GET /v1/model-info`.

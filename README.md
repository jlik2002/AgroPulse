# AgroPulse

Веб-сервис дистанционного мониторинга сельскохозяйственных полей.

Пользователь находит регион на карте, выбирает готовый контур пашни или рисует
полигон вручную. Дальше сервис сам получает спутниковые (Sentinel-2) и
метеорологические данные, строит временной ряд NDVI, восстанавливает пропущенные
наблюдения обученной моделью, находит негативные аномальные периоды и
прогнозирует риск ухудшения на 14 дней. Результат — интерактивная аналитика,
выгрузка CSV и PDF-отчёт.

Поля принадлежат хозяйствам, и над полем есть второй уровень выводов: индекс
потребности в поддержке по хозяйству, реестр хозяйств, ранжированный по этому
индексу, и заключение о состоянии угодий — материал для комиссии, решающей
о государственной поддержке.

Вторая точка запуска — batch-инференс: восстановление скрытых значений NDVI по
готовому CSV (раздел [Batch-инференс](#batch-инференс-задача-1)).

## Стек

| Слой | Технологии |
|---|---|
| Бэкенд | FastAPI, Pydantic v2, SQLAlchemy 2, Alembic |
| Очередь задач | Celery + Redis, две очереди: `collect` и `analyze` |
| Хранение | PostgreSQL 16 + PostGIS, MinIO (S3-совместимое) |
| Спутниковые данные | Google Earth Engine (Sentinel-2) |
| Погода | Open-Meteo (архив ERA5 и прогноз на 14 дней) |
| Контуры полей | OpenStreetMap / Overpass API |
| Восстановление пропусков | CatBoost, модель V6 (обучена заранее, артефакты в репозитории) |
| LLM | OpenRouter — только пересказ проверенных расчётов |
| Отчёты | WeasyPrint и Jinja2 для PDF, matplotlib для графиков |
| Фронтенд | React 18, TypeScript, Vite, Tailwind CSS, Radix UI |
| Карта и графики | Leaflet и leaflet-geoman, подложки CARTO и Esri, ECharts |
| Окружение | Docker Compose |

# Запуск

## Что нужно заранее

| Требование | Как проверить |
|---|---|
| Docker Engine 24+ с плагином Compose v2 | `docker compose version` |
| ~8 ГБ свободного места на диске | `df -h .` |
| ~4 ГБ свободной оперативной памяти | `free -h` |
| Свободные порты 5173, 8000, 5432, 6379, 9000, 9001 | `ss -ltn` |
| Доступ в интернет из контейнеров | шаг 8 |
| Аккаунт Google Cloud (бесплатный) | шаг 3 |

Ничего, кроме Docker, ставить не нужно: Python, Node и все зависимости живут
внутри образов.

## Шаг 1. Получить код

```bash
git clone <адрес репозитория> agropulse
cd agropulse
```

Все команды ниже выполняются из корня репозитория — там, где лежит
`docker-compose.yml`.

## Шаг 2. Создать файл окружения

```bash
cp .env.example .env
```

Файл `.env` уже содержит рабочие значения для локального запуска. Править в нём
нужно две строки, и обе — на шагах 3 и 5. Пароли из примера принимаются только
при `APP_ENV=local`; в `dev` и `prod` сервис откажется стартовать со значениями
по умолчанию.

## Шаг 3. Подключить Google Earth Engine

Спутниковые снимки сервис берёт только из Earth Engine. **Без ключа контейнеры
поднимутся и интерфейс откроется, но обработка любого поля завершится ошибкой
сбора данных.** Реализация поверх STAC в репозитории есть и проверена, но в
цепочку источников сознательно не включена — она на порядок медленнее
(`backend/agropulse/providers/chain.py`).

**3.1.** Откройте [Google Cloud Console](https://console.cloud.google.com),
создайте проект и скопируйте его **Project ID** (не название — именно ID,
например `agropulse-471203-k7`).

**3.2.** Зарегистрируйте проект в Earth Engine:
<https://console.cloud.google.com/earth-engine> → *Register* → выберите
**noncommercial** (для учебных и исследовательских задач бесплатно).

**3.3.** Включите Earth Engine API:
<https://console.cloud.google.com/apis/library/earthengine.googleapis.com> →
*Enable*.

**3.4.** Создайте сервис-аккаунт:
<https://console.cloud.google.com/iam-admin/serviceaccounts/create>.
Выдайте ему две роли: **Earth Engine Resource Viewer** и
**Service Usage Consumer**.

**3.5.** Выпустите ключ: откройте созданный сервис-аккаунт → вкладка *Keys* →
*Add key* → *Create new key* → формат **JSON** → *Create*. Файл скачается сам.

**3.6.** Положите скачанный файл в репозиторий под точным именем:

```bash
cp ~/Downloads/<скачанный-файл>.json secrets/gee-service-account.json
```

Имя менять нельзя — по нему файл ищется внутри контейнера. Каталог `secrets/`
в репозиторий не попадает.

**3.7.** Впишите Project ID из шага 3.1 в `.env`:

```
GEE_PROJECT=agropulse-471203-k7
```

## Шаг 4. Положить опорный набор задачи 1

Модель восстановления пропусков V6 сравнивает поле с другими полями той же
даты — её признаки межполевые. Поэтому опорный набор нужен ей и при
предсказании, а не только при обучении.

```bash
cp /путь/к/train_dataset.csv data/
```

Файл в репозиторий не входит (каталог `data/` в `.gitignore`). Без него сервис
работает, но пропуски NDVI заполняет грубым приближением по соседним точкам —
источник значения при этом честно показывается в интерфейсе.

## Шаг 5. Ключ OpenRouter (необязательно)

LLM только пересказывает уже посчитанные числа, со сверкой их с расчётом. Без
ключа считается всё, кроме текстовых пояснений. Ключ берётся на
<https://openrouter.ai/keys> и вписывается в `.env`:

```
OPENROUTER_API_KEY=sk-or-v1-...
```

## Шаг 6. Собрать и запустить

```bash
docker compose up -d --build
```

Первая сборка занимает 5–15 минут: собираются образ бэкенда (Python 3.12 плюс
системные библиотеки WeasyPrint) и образ фронтенда (сборка SPA в Node 22).
Повторные запуски — секунды.

Порядок подъёма задан healthcheck'ами, отдельных скриптов ожидания не нужно:
`postgres` → `migrate` (накатывает миграции и завершается) → `api`, воркеры →
`web`.

## Шаг 7. Дождаться готовности

```bash
docker compose ps
```

Ожидаемое состояние:

| Сервис | Состояние |
|---|---|
| `postgres`, `redis`, `minio`, `api`, `web` | `running (healthy)` |
| `worker-collect`, `worker-analyze` | `running` |
| `migrate` | `exited (0)` — так и должно быть, это одноразовая задача |

## Шаг 8. Проверить, что всё работает

**8.1. Бэкенд видит базу и хранилище:**

```bash
curl http://localhost:8000/health/ready
# {"status":"ok","checks":{"postgres":true,"s3":true}}
```

**8.2. Доступ к Earth Engine — вся цепочка до реальных данных:**

```bash
docker compose run --rm api python /app/scripts/check_gee.py
```

Скрипт проходит пять шагов: читает ключ, проверяет Project ID, инициализирует
Earth Engine, находит снимки и считает средний NDVI по тестовому полигону. На
каждом шаге он сообщает, что именно не так. Успешное завершение означает, что
доступ настроен полностью.

**8.3. Внешние источники данных достижимы из контейнера:**

```bash
docker compose run --rm --no-deps api sh /app/scripts/check_network.sh
```

Колонка `http`: 200 или 404 — хост отвечает; `000` — соединение не установлено.

## Шаг 9. Открыть

| Адрес | Что это |
|---|---|
| <http://localhost:5173> | веб-интерфейс |
| <http://localhost:8000/docs> | документация API |
| <http://localhost:9001> | веб-консоль MinIO, логин и пароль — `S3_ACCESS_KEY` и `S3_SECRET_KEY` из `.env` |

Регистрации нет: при первом заходе сервис ставит cookie с анонимным
идентификатором и приписывает к нему создаваемые проекты.

## Шаг 10. Пройти сценарий в интерфейсе

1. **Поля.** Найдите регион по названию или введите координаты. Возьмите
   готовый контур пашни из OpenStreetMap либо нарисуйте полигон. Укажите
   хозяйство-владельца (его можно завести прямо в карточке поля) и культуру —
   без них поле не создаётся. Задайте период анализа.
2. **Проверка параметров.** Отметьте поля для расчёта. По умолчанию отмечены
   только непосчитанные: сбор по каждому полю занимает минуты.
3. **Обработка.** Прогресс по пяти шагам для каждого поля отдельно. Готовое
   поле открывается, не дожидаясь остальных.
4. **Хозяйства.** Реестр приоритетной поддержки: хозяйства ранжированы
   по индексу потребности, рядом с каждым — достоверность заключения и
   предлагаемое действие. Хозяйства без заключения вынесены отдельным списком,
   а не поставлены в конец очереди. Карточка хозяйства собирает заключение PDF
   и хранит список сформированных документов.
5. **Сводка.** Карта с окрашенными контурами и очередь на осмотр, ранжированная
   по составному риску отдельных полей.
6. **Поле.** Вкладки «Обзор», «Снимки», «Динамика», «Данные».
7. **Прогноз.** Линия на 14 дней с коридором вероятных значений и факторами
   влияния.
8. **Отчёты.** Четыре уровня документа — поле, хозяйство, реестр, сводка
   по проекту. Выбор разделов, сборка PDF, предпросмотр готового документа.

# Batch-инференс (задача 1)

Восстановление скрытых значений `primary_ndvi` по готовому файлу. Работает тем
же клиентом моделей, что и веб-сценарий.

**1.** Положите в каталог обмена `data/` два файла:

```bash
cp private_features.csv train_dataset.csv data/
```

`train_dataset.csv` обязателен — см. шаг 4 выше.

**2.** Сформируйте `submission.csv`:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" api \
  python -m agropulse.cli predict \
    --input /app/data/private_features.csv \
    --output /app/data/submission.csv
```

Флаг `--user` нужен, чтобы результат принадлежал вам, а не пользователю
контейнера.

**3.** Проверьте формат перед загрузкой на платформу:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" api \
  python -m agropulse.cli validate \
    --input /app/data/private_features.csv \
    --submission /app/data/submission.csv
```

Готовый файл — `data/submission.csv` в каталоге репозитория.

# Если что-то не работает

| Симптом | Причина и что делать |
|---|---|
| `port is already allocated` при `up` | Порт занят другим процессом. Освободите его или поменяйте левую часть в разделе `ports` нужного сервиса в `docker-compose.yml`. |
| `migrate` в состоянии `exited (1)` | Миграции не накатились, `api` не поднимется: `docker compose logs migrate`. |
| `/health/ready` отдаёт `"s3":false` | MinIO не поднялся: `docker compose logs minio`. |
| Обработка поля падает на сборе данных | Чаще всего ключ Earth Engine. Запустите проверку из шага 8.2 и посмотрите `docker compose logs worker-collect`. |
| Пустой временной ряд, поле «без данных» | Снимков за период нет либо все закрыты облаками. Расширьте период анализа. |
| Внешние API недоступны, TLS-хендшейк виснет | MTU сети контейнеров занижен до 1400 намеренно (см. комментарий в конце `docker-compose.yml`). Проверьте шагом 8.3. |
| Пропуски восстановлены «приближением по соседним точкам» | Нет `data/train_dataset.csv` — шаг 4. В логах `api` будет `ml_v6_reference_missing`. |
| Нет текстовых пояснений | Не задан `OPENROUTER_API_KEY` — шаг 5. |
| Правки в задачах Celery не применяются | Воркеры не перезагружаются сами: `docker compose restart worker-collect worker-analyze`. |

Общий журнал: `docker compose logs -f api worker-collect worker-analyze`.

# Разработка

Код смонтирован в контейнеры, uvicorn перезагружается автоматически.

```bash
docker compose logs -f api                  # логи
docker compose restart worker-collect       # перезапуск воркера после правок задач
docker compose run --rm api pytest          # тесты
docker compose run --rm api ruff check .    # линтер
```

Локальный образ собирается с `INSTALL_DEV=true` и несёт pytest и ruff; образ для
эксплуатации остаётся без инструментов разработки.

Интеграционные тесты создают отдельную базу `${POSTGRES_DB}_test`, накатывают на
неё миграции и удаляют её после прогона — так проверяется и то, что миграции
применяются на пустой базе. Если PostgreSQL недоступен, эти тесты пропускаются,
а модульные продолжают работать.

Фронтенд удобнее разрабатывать вне контейнера: Vite отдаёт горячую перезагрузку,
а запросы к `/api` проксирует на поднятый Compose'ом бэкенд.

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173
npm run typecheck  # проверка типов
npm run build      # та же сборка, что и в образе web
```

Адрес бэкенда для прокси задаётся переменной `VITE_API_PROXY` (по умолчанию
`http://localhost:8000`). В собранный образ адрес не зашит: путь `/api`
проксирует nginx внутри контейнера `web`.

Новая миграция после изменения моделей:

```bash
docker compose run --rm --user "$(id -u):$(id -g)" migrate \
  alembic revision --autogenerate -m "описание изменения"
docker compose run --rm migrate alembic upgrade head
```

Устройство слоёв и принятые при рефакторинге решения — в
[`docs/REFACTORING.md`](docs/REFACTORING.md).

# Как устроен сервис

```
api              FastAPI: REST и поток прогресса SSE, долгих операций не выполняет
worker-collect   Celery: обращения к GEE и Open-Meteo. Упирается в сеть
worker-analyze   Celery: климатология, аномалии, риск, отчёты. Упирается в CPU
postgres         PostGIS: полигоны полей, наблюдения, аномалии, прогнозы
redis            брокер Celery, кэш внешних API, шина прогресса
minio            PDF-отчёты, превью снимков, кэш растров
web              nginx: раздача React-приложения и проксирование /api
```

Миграции выполняет отдельный шаг (`migrate` в Compose), а не старт приложения:
иначе несколько реплик API пошли бы накатывать их наперегонки.

## Модель восстановления пропусков

Пропуски NDVI восстанавливает модель **V6**: CatBoost предсказывает поправку к
линейной опоре, приведённой к шкале конкретного прибора, а предсказания трёх
приборов сворачиваются вероятностями классификатора съёмки. Устройство модели,
происхождение кода и её ограничения — в
[`backend/agropulse/ml/v6/README.md`](backend/agropulse/ml/v6/README.md).

Модель обучена заранее, её артефакты лежат в репозитории рядом с кодом.
**Обучение в сервисе не запускается никогда** — выполняется только предсказание.
Один и тот же клиент обслуживает и веб-сценарий, и batch-инференс: расхождение
между ними означало бы, что проверяется одно, а работает другое.

Прогноз вперёд V6 не делает — она восстанавливает точку между наблюдениями.
Прогноз считает климатический метод (`ml/climatology_forecast.py`), и его
источник показывается пользователю отдельно.

Запасной путь — внешний сервис моделей по контракту
[`docs/ML_API.md`](docs/ML_API.md), включается при `ML_V6_ENABLED=false`.

## Структура репозитория

```
backend/
  agropulse/
    main.py            точка входа FastAPI

    api/routers/       HTTP-эндпоинты
    providers/         внешние источники данных за общими интерфейсами
    features/          построение признаков для модели
    ml/                модель V6, клиент ML-сервиса и локальный baseline
    analytics/         климатология, аномалии, составной риск

    reports/           выгрузка CSV и генерация PDF
    storage/           объектное хранилище артефактов
    tasks/             задачи Celery
    cli.py             batch-инференс
  migrations/          миграции Alembic
  tests/               модульные и интеграционные тесты
frontend/
  src/
    api/               клиент REST и подписка на поток прогресса
    app/               оболочка проекта и общий контекст
    components/        карта, графики, интерфейсные примитивы
    pages/             экраны пользовательского сценария
    lib/               форматирование, статусы, разбор временного ряда
  nginx.conf.template  раздача SPA и проксирование /api
scripts/               проверка доступа к GEE и к внешним API
docs/                  план работ, контракт с ML-сервисом, исследование
data/                  каталог обмена файлами для batch-инференса
secrets/               ключ сервис-аккаунта GEE
```

## Лицензии и источники данных

Все внешние источники открытые: Copernicus Sentinel-2, ERA5 через Open-Meteo,
OpenStreetMap (ODbL), ESA WorldCereal. Перечень используемых коллекций и
параметров предобработки — в [`docs/RESEARCH.md`](docs/RESEARCH.md).

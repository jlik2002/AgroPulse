## Блокирующее

### 1. Каталог `frontend/src/lib/` не попал в коммит

```
$ git check-ignore -v frontend/src/lib/format.ts
.gitignore:17:lib/	frontend/src/lib/format.ts
```

Правило `lib/` из Python-секции `.gitignore` (осталось от pyenv/virtualenv) молча
съело 7 файлов, 588 строк: `cn.ts`, `crops.ts`, `format.ts`, `geo.ts`, `project.ts`,

```
$ git archive feature/e7-frontend frontend/src | tar -t | grep -c 'src/lib'
0
```

Их импортируют 47 из 66 файлов фронтенда. На чистом клоне `docker compose up --build`
упадёт на `npm run build` — а это прямой критерий «запуск по README без правок
исходников». Локально всё работает только потому, что файлы лежат в рабочем каталоге.

Чинится строкой `!frontend/src/lib/` в `.gitignore` (или сужением правила до `/lib/`)
и `git add -f`.

## Корректность и бизнес-логика

### 2. «Ожидаемая динамика» рисуется по прогнозным точкам

`frontend/src/components/charts/NdviChart.tsx:61-67` — фильтр берёт любые точки
с непустыми `ndvi_lo`/`ndvi_hi`, не исключая прогноз.

У этих колонок два разных смысла, и бэкенд фиксирует это явно
(`repositories/observations.py:129`): у исторических точек это коридор нормы
`медиана ± σ`, у прогнозных — доверительный интервал модели
(`services/pipeline.py:686`). Середина интервала прогноза равна самому прогнозу.
Значит серая пунктирная «ожидаемая сезонная норма» на горизонте прогноза просто
повторяет линию прогноза — и визуально «подтверждает» его сама собой.

`DynamicsTab.tsx:59` передаёт именно `series.all` с включённым по умолчанию
`showExpected`, то есть на главном экране динамики это видно всегда.

Правильная реализация уже написана — `lib/series.ts:expectedCurve()` фильтрует
`value_type !== "forecast"` — и нигде не используется (0 вызовов).

Тот же корень у стыковки коридора прогноза (`NdviChart.tsx:79-90`): затравочная
точка `lastFact` — наблюдение, у неё `ndvi_lo/hi` это границы нормы, поэтому лента
прогноза стартует шириной 2σ климатологии.

### 3. Слой «RGB» показывает подложку Esri вместо снимка

`FieldStatePanel.tsx:49-51` — в режиме `rgb` контур делается прозрачным, и под ним
остаётся базовая подложка `World_Imagery`. Подпись: «Снимок в естественных цветах».

На вкладке «Снимки» пользователь выбирает дату в ленте, переключается на RGB
и видит одну и ту же недатированную мозаику Esri для любой даты, рядом с надписями
«Облачность 12% · Покрытие 87%». В режиме сравнения обе панели показывают
идентичную картинку под двумя разными датами.

Для NDVI/NDMI честность соблюдена — есть tooltip «средняя оценка, а не карта
неоднородности». У RGB такой оговорки нет, и подпись утверждает обратное.

Варианты: убрать режим RGB до появления настоящих тайлов либо подключить
`ee.Image.getMapId()` — XYZ-тайлы GEE ложатся обычным `TileLayer`.

### 4. Упавшее поле навсегда остаётся «в обработке»

`services/pipeline.py:583` `mark_failed()` ставит `FieldStatus.FAILED`, но не
публикует `field_done` — этот вызов есть только на успешной ветке
(`pipeline.py:284`).

`ProcessingPage.tsx:56-58` исключает `failed` из готовности:

```ts
ready: progress.finished.has(field.id) ||
       (field.status !== "pending" && field.status !== "failed"),
```

Итог: прогресс-бар не доходит до конца, «Осталось около N минут» не исчезает,
а `useEffect` продолжает дёргать `refetchFields` каждые 5 секунд бесконечно.
После перезагрузки страницы `finished` пуст, и поле не показывает состояния
«Ошибка» из `StatusPill` — только вечный спиннер.

### 5. Предупреждение о восстановленных значениях никогда не показывается

`ForecastPage.tsx:264` читает `stats.restored_points`. В `TimeseriesRead.stats`
такого ключа нет — там `restored` (`services/fields.py:216`). `restored_points`
есть только в `FieldSummary`, это другой эндпоинт.

`stats` типизирован как `Record<string, number | null>`, поэтому TypeScript
промолчал. Блок «Часть ряда восстановлена моделью — надёжность прогноза ограничена
качеством исходных наблюдений» выключен всегда. Это ровно та честная оговорка,
ради которой раздел «Ограничения» и делался.

### 6. «Пик риска» на здоровом поле

`ForecastPage.tsx:buildDayRisk` нормирует NDVI по min/max внутри самого горизонта
прогноза. При прогнозе 0.78→0.82 нижняя треть дней всё равно получает подпись
«Высокий», красную рамку и бейдж «Пик риска» с красным кольцом.

Комментарий честно говорит «абсолютной шкалы у прогноза нет» — но следствие в том,
что интерфейс генерирует ложную тревогу на каждом благополучном поле. Абсолютная
привязка есть: `ndvi_zscore` и коридор нормы лежат в тех же записях.

### 7. Поле с ошибкой в сводке: «Отклонений не найдено»

`SummaryPage.tsx:261-265` — три ветки: аномалия, `insufficient_data`, всё остальное.
В «всё остальное» попадают `failed` и `pending`, и карточка сообщает «Отклонений
от ожидаемой динамики не найдено». `project_summary` отдаёт все поля проекта,
включая необработанные.

### 8. Проект, где все поля без данных, теряет «Сводку» и «Отчёты»

`ProjectLayout.tsx:31-34`:

```ts
const processed = fields.some(f => f.risk_score !== null || f.status === "normal")
```

У полей со статусом `insufficient_data` `risk_score` равен `None` намеренно
(«искусственного балла не получают», `services/analysis.py`). Если ни одно поле
не набрало данных, `processed === false`, и оба пункта навигации остаются
заблокированными навсегда — при том, что сводка это единственный экран, который
объяснил бы, чего именно не хватило.

Надёжнее считать по `status !== "pending"`.

### 9. Подписи снимков привязаны к сторонам, а не к данным

`ScenesTab.tsx:145-152` — левая панель всегда «До аномалии» с зелёным чипом, правая
всегда «Последнее наблюдение» с красным. На поле без аномалий это ложный сигнал.
А после нажатия кнопки обмена (строка 153) даты меняются местами, подписи нет,
и более ранний снимок оказывается подписан «Последнее наблюдение».

### 10. `RISK_LEVEL_TITLES.low = "Средний"`

`lib/status.ts:97-101`. Прогноз с уровнем `low` выводится как «Средний риск» —
завышение на ступень. Используется на `ForecastPage` и в шапке `OverviewTab`.

## Существенное

### 11. Предпросмотр отчёта показывает не тот документ

`ReportPreview.tsx` — вторая, независимая от `field_report.html` реализация первой
страницы. Docstring обещает: «пользователь видит настоящий документ, а не
абстрактный макет». Фактически:

- «Краткий вывод» в PDF генерирует LLM, а в предпросмотре — захардкоженные фразы
  («С 13 мая наблюдается устойчивое снижение NDVI»). В скачанном файле будет
  другой текст.
- Чекбоксы разделов на предпросмотр не влияют вообще — меняется только список
  справа.

Либо честнее назвать это «состав документа» (как уже сделано для сводного отчёта —
`ProjectPreviewStub`), либо строить предпросмотр из того же PDF первой страницей.

### 12. «Что влияет на прогноз» строится из факторов текущего риска

`ForecastPage.tsx:65` берёт `risk.breakdown` — разложение составного риска текущего
состояния. У `ForecastRead` есть собственное поле `factors`, добавленное в этой же
ветке (`schemas/analysis.py:66`), и оно не используется во фронтенде ни разу.
Раздел называет причины прогноза тем, что объясняет прошлое.

### 13. Ошибка поиска контуров выглядит как «контуров нет»

`FieldsPage.tsx:190-196` — состояние `searchParcels.isError` не обрабатывается, есть
только `isPending` и длина результата. Упавший или отвалившийся по таймауту Overpass
показывает «В этом районе готовых контуров нет — нарисуйте поле вручную».

Отдельно: `loadParcels` берёт `map.getBounds()` без ограничения по зуму, так что
с континентального масштаба уходит запрос на bbox в тысячи километров.

### 14. Дубли контуров OSM после перезагрузки

`FieldsPage.tsx:64-67` — `addedRefs` живёт только в памяти вкладки, потому что
`FieldRead` не отдаёт `external_ref`. После F5 уже добавленные контуры снова
предлагаются, и поле создастся вторым экземпляром. Проще всего добавить
`external_ref` в `FieldRead` — он уже есть в модели и в `FieldCreate`.

### 15. Период проекта меняется после анализа, без предупреждения и без обработки ошибки

`ProjectService.update()` (`services/projects.py:60`) документирован как «правка
до запуска анализа», но ничем это не проверяет. `DateRange` на `FieldsPage.tsx:255`
шлёт PATCH сразу по изменению. После смены периода уже посчитанные аномалии, риск
и прогноз относятся к старому окну, а шапка показывает новое.

Ошибку PATCH никто не показывает: при периоде короче 14 дней прилетает 422
`invalid_period`, `updateProject.error` нигде не читается, поле просто откатывается
к серверному значению без объяснения.

### 16. Удаление поля без подтверждения

`FieldsPage.tsx:239` — `onDelete={() => deleteField.mutate(field.id)}`, кнопка
в карточке списка. Каскадом уносит все наблюдения, аномалии и прогнозы поля.
Отмены нет.

### 17. `useProjectProgress` не сбрасывает состояние при смене проекта

`api/progress.ts:57-99` — в cleanup закрывается `EventSource` и сбрасывается
`connected`, но `snapshot`, `events`, `finished` и `logRef.current` остаются.
При переходе в другой проект без перезагрузки страницы в `byField` подмешиваются
поля предыдущего проекта, и лента событий продолжается чужой историей. Сценарий
достижим: кнопка «Новый анализ» на `SummaryPage`.

Там же: массив `events` растёт неограниченно, и `useMemo` пересобирает состояние
всех полей на каждое событие.

### 18. У готового поля все стадии красятся в «выполнено»

`ProcessingPage.tsx:203` `forcedDone={activeRow.ready}` перебивает реальный статус
каждой стадии. Поле, завершившееся со статусом `insufficient_data`, показывает пять
зелёных галочек — стадия, сообщившая о нехватке снимков, выглядит успешной.

### 19. Зелёная галочка у любого качества данных

`SummaryPage.tsx:301` и `OverviewTab.tsx:129` — `CircleCheck` в цвете `text-ok`
рядом с текстом, который может быть «низкое» или «неизвестно». Иконка противоречит
подписи.

### 20. `region.bbox` игнорируется

`FieldsPage.tsx:107` — `onRegionSelect` делает `flyTo([lat, lon])` на зум 13.
Бэкенд специально возвращает `bbox` (`RegionRead`), чтобы можно было вписать регион
в экран. Выбор «Краснодарский край» приземляет пользователя на случайное поле
в его центре.

### 21. Тройной опрос поверх SSE

`ProjectLayout.tsx:22` — `refetchInterval: 15_000` на списке полей всегда, на всех
экранах проекта. Плюс `ProcessingPage.tsx:73` — свой `setInterval` на 5 секунд.
Плюс `SummaryPage.tsx:40` — `refetchInterval: 20_000`. SSE-поток задумывался, чтобы
этого не делать.

### 22. Захардкоженная рекомендация в карточке прогноза

`OverviewTab.tsx:209` — при `direction === "declining"` подпись «Риск сохранится
высоким без корректирующих мер». Это причинно-следственное утверждение и намёк
на вмешательство. Промпты LLM такое запрещают явно (`llm/prompts.py`, «ЗАПРЕЩЕНО:
утверждать причину как факт», «рекомендовать … конкретные агротехнические
назначения») — интерфейсу стоит держать ту же планку.

## Что сделано хорошо

- **`set_climatology`** (`repositories/observations.py`) — разделение прогнозных
  и исторических строк при записи нормы сделано осознанно, объяснено в docstring
  и покрыто тестом `test_analyze_keeps_forecast_interval_intact`.
- **`_norm_bands` = медиана ± σ**, то есть ровно порог `z = −1`. График и найденные
  аномалии не могут противоречить друг другу по построению, и на это есть тест.
- **SSE**: снимок первым сообщением, heartbeat раз в 15 с, отдельное
  Redis-соединение на подписку, корректный `finally` с `unsubscribe`/`aclose`.
  `proxy_buffering off` и `proxy_read_timeout 3600s` в nginx — та часть, которую
  почти всегда забывают.
- **Разделение происхождения значений** (`observed`/`restored`/`forecast`) проведено
  сквозь типы, легенды, таблицу и фильтры — кроме двух мест, названных выше.
- Двухэтапный Dockerfile с отдельным слоем `npm ci`, `manualChunks` для echarts
  и leaflet, `/healthz` без обращения к бэкенду.
- Типы `api/types.ts` сверены со схемами вручную и разошлись ровно в одном ключе.
- Комментарии объясняют почему, а не что: `unmask(0, False)`, MTU 1400,
  `_ensure_initialized` по PID.
